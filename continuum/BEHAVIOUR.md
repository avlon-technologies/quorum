## What this document never says

- That anything runs concurrently, or in which interleaving: *unordered* is the model's silence about order, not a scheduling claim. The implementation chooses (and may serialize).
- How long anything takes, when a consequence is emitted, or whether emission is synchronous with consumption.
- That any Event occurs, that a Workflow completes, or that a trace "succeeds": `closed` is declared causal closure only.
- Anything inferred from names, types or textual likeness. Where the model declares nothing, the line says so.

Meanings, verbatim from the analysis:

- `before`: a transition path leads from the first step to the second: along that path the second activates after the first completes. Under an any-join the second may fire from another branch first (WORKFLOW-SEMANTICS §4.1); this is order along the declared path, never timing
- `unordered`: no transition path leads from either step to the other — the static potential-concurrency relation of WORKFLOW-SEMANTICS §9.7 C4. The model declares no order between them. Whether both activate in one run depends on guards and selections; whether they run concurrently, and in what interleaving, is the implementation's — never a claim of this analysis
- `loop`: mutually reachable inside a loop: ordered within one iteration; iterations are causally totally ordered (§5.3)
- `ranks`: a rendering device only — the longest transition path from the trigger, back edges excluded. Steps of one rank are pairwise unordered; steps of different ranks are NOT necessarily ordered (the pair relation is authoritative for that)
- `fanOut`: several steps follow one point. From a DecisionStep exactly one is selected (§3.1.1: alternatives, never both). Otherwise each transition settles on its own (§3.1): the steps that activate are unordered among themselves
- `join`: `all`: the round fires when every incoming transition has settled and at least one fired; `any`: it fires on the first fired settlement and absorbs the rest (§4.1). The join is the declared synchronization point, nothing more
- `wait`: the activation pends until exactly one alternative resolves it — an Event correlated to the instance, or the deadline (ADR-0015). Which one, and when, is runtime
- `entry`: the entry steps activate from the trigger fact (§4.1); several entry steps are unordered among themselves
- `causal-relation-undeclared`: the participant consumes the message and emits others but declares no Reaction for that consumption: the model does not say what, if anything, follows. The implementer will decide unless the architecture declares it (METAMODEL §5.2 Reaction) or records the silence as a gap
- `continuity-undeclared`: an authored Reaction names the consequence but declares no correlation: the model does not say WHICH consequence instance follows WHICH consumed instance. A `correlate` clause (CorrelationContinuity) would make the hop correlated
- `exclusivity-not-established`: the Workflow's definition names several consequences for this consumption and does not prove that exactly one is emitted per run (causality.js one-of proof). The model does not establish exclusivity; a reader must not assume it
- `unconsumed-message`: the trace reaches a message that no participant consumes and no Reaction declares as a sink: the model is silent about whether anything happens next. A declared sink (`on X -> none`) would make the end explicit
