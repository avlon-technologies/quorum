### Policys (3)

#### `::Quorum.ResearchFunding.BlindReview` — Policy

> No reviewer sees another reviewer's scores or comments, directly, through the portfolio or through a notification, before their own review of that proposal is submitted. Officers and chairs see all submitted reviews.

#### `::Quorum.ResearchFunding.HumansDecide` — Policy

> Eligibility, assignment and award are human decisions. Automation proposes, detects and escalates; it never decides.

#### `::Quorum.ResearchFunding.RoleScopedAccess` — Policy

> Deny by default. Every operation names the roles that may call it and the resources each role is scoped to: applicants their own proposals, reviewers their own assignments, officers and chairs the whole funding programme. Roles are read from the account store on every request.

### BusinessRules (10)

#### `::Quorum.ResearchFunding.Adjudication.ChairOnScoredOnly` — BusinessRule

- statement = A panel decision is recorded only by an account holding the panel_chair role, only for a proposal with an open adjudication case (which exists only once the proposal is scored), only once, and an award only when no integrity hold is on the case.

#### `::Quorum.ResearchFunding.Adjudication.EnvelopeNotExceeded` — BusinessRule

- statement = An award commits its amount only by a single conditional write on the call's ledger row that succeeds only if committed + amount <= envelope; otherwise nothing is recorded and the case returns to the chair.

#### `::Quorum.ResearchFunding.Notification.NoScoresToReviewers` — BusinessRule

- statement = A notification addressed to a reviewer never carries another reviewer's scores or comments.

#### `::Quorum.ResearchFunding.PeerReview.AssignmentValidity` — BusinessRule

- statement = An assignment is valid only if: the proposal is assignable (confirmed eligible and not withdrawn); the reviewer holds the reviewer role; their ORCID is verified (asked of Identity in the same transaction); no conflict is declared between them and the proposal; they are not the proposal's applicant; they hold no other active assignment to it; and the proposal has fewer than three active assignments.

#### `::Quorum.ResearchFunding.PeerReview.EveryCriterionScored` — BusinessRule

- statement = A review is submitted only if it carries exactly one score for every criterion published on the call, each an integer from 1 to 5.

#### `::Quorum.ResearchFunding.PeerReview.PeerReviewsHiddenUntilOwnSubmitted` — BusinessRule

- statement = Another reviewer's scores and comments on a proposal are returned to a reviewer only if that reviewer's own review of the proposal is submitted.

#### `::Quorum.ResearchFunding.PeerReview.ThreeSubmittedReviews` — BusinessRule

- statement = ProposalFullyReviewed is published once, when the count of submitted reviews on non-revoked assignments of the proposal reaches exactly three.

#### `::Quorum.ResearchFunding.Submission.ApplicantScope` — BusinessRule

- statement = An applicant reads and changes only proposals whose applicantId is their own account; any other proposal is reported as not found.

#### `::Quorum.ResearchFunding.Submission.SubmissionWindowOpen` — BusinessRule

- statement = SubmitProposal is accepted only while the proposal's call is open and the current instant is strictly before the call's deadline; checked against the call store inside the submitting transaction.

#### `::Quorum.ResearchFunding.Submission.SubmittedOnce` — BusinessRule

- statement = SubmitProposal moves draft -> submitted and nothing else; a proposal not in draft is refused with already_submitted. Withdrawal is the only way back out, and it is terminal.

### Derived behavioural traces

The traces in `acceptance/traces/` are the compiler's DERIVED process graph from the scenario's starting message: every hop classified as the model declares it (`reactive` / `correlated` where a Reaction or a Workflow establishes the consequence; `causal relation undeclared` where only topology connects them). A trace is architectural knowledge, not a runtime claim: it does not say what happens concurrently, how long anything takes, or that any event occurs. Where a scenario also carries an authored `expectedTrace`, that is the scenario author's expectation and is labelled as such.

### The behavioural projection — `BEHAVIOUR.md`

`BEHAVIOUR.md` is the same knowledge drawn for a reader: from each scenario's starting message, the trace as a tree, every Workflow it passes through expanded into its steps with the static order relation the definition establishes (which steps a transition path orders, which it leaves UNORDERED — potentially concurrent, statically, WORKFLOW-SEMANTICS §9.7 C4 — and where joins, exclusive decisions and waits synchronize), and the underspecified-causality findings: 1 along these traces. Every line says whether it is DECLARED, DERIVED or UNSPECIFIED. "Unordered" is the model's silence about order, never a scheduling claim: you choose whether unordered steps run concurrently, and you record the choice as an implementation policy, not as architecture. Each finding is a decision you would otherwise make silently — declare it (a Reaction, a correlation, a sink) or record it as a gap.

## 6. Semantic gaps — when the architecture is silent

If implementing requires a behaviour, message, store, consumer, ordering or rule the model does not declare:

1. **Do not invent it silently.** An undeclared claim implemented anyway is the defect this package exists to prevent.
2. Record the gap as `gaps/<yyyy-mm-dd>-<slug>.md` in the implementation repository: the one precise fact the architecture cannot currently express or does not declare; the evidence (which scenario, which element); the smallest change that would close it; and what the implementation does meanwhile (nothing, a feature flag, a fake).
3. Request an architecture change: a `.adl-change` whose `base` pins this package's state —

```
base package avlon.quorum version "package-1" state "sha256:d95dfab0d6c84f716ac2c18865454637984cd332ce2619018bdb93aa06a7b3ba"
```

4.
